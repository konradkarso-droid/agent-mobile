## 0. Как работаем

- **По одному шагу.** Одна правка — одна сборка — одно измерение. Не выдавать многошаговые пачки.
- **Полный файл перед полной заменой.** Не предлагать замену файла, не увидев его текущее содержимое целиком. Прецедент: частичная видимость однажды съела 77 строк. За эту сессию правило сработало ещё раз — `RiskTriggerTest.kt` уже существовал с шестью проверками, замена вслепую стёрла бы их молча, при зелёном CI.
- **Пути от корня репозитория** каждый раз, а не имя файла.
- **Код — файлами на скачивание**, не текстом в чат.
- **Ответы по-русски.**
- **Один коммит — один файл.** Веб-редактор GitHub иначе не умеет; при многофайловой правке порядок такой, чтобы каждый промежуточный коммит компилировался.
- **Не называть цифру, не проверив, чем она меряется.** Нарушено дважды 29-го и ещё раз 30-го (см. §7).
- **Записи памяти о прошлых чатах — не состояние `main`.** Перед действием сверяться с репозиторием.
- **Комментарии пишутся для постороннего, который не читал обсуждений.** В коде остаётся то, что верно само по себе: почему так устроено, чего механизм не умеет, где границы починки. Даты, «проход №N», история замеров и ход разговора идут в хендовер. Одно объяснение живёт в одном месте, остальные ссылаются на него — две копии со временем расходятся, и не видно, какая врёт.

Пользователь не программист по образованию. Всякий механизм обязан давать сигнал, читаемый без знания программирования.

**Новое: `CHECKLIST.md` в корне репозитория** — восемь принципов разработки, выведенных на этом проекте, у каждого проверяемый вопрос. Прогонять до написания кода на больших задачах и на застрявших развилках. Прогон переставляет план, а не подтверждает его; план, вышедший неизменным, — повод перечитать ответы.

## 2. Что сделано по существу

### 2.1 Отбор слепнул на заглавную букву — ЗАКРЫТО

`LIKE` в SQLite нечувствителен к регистру **только для латиницы**; кириллицу он сравнивает побайтно. Слова вопроса приводились к нижнему регистру в `meaningfulWords`, содержимое записи — нигде. Слово, стоящее в записи с заглавной буквы, для поиска не существовало.

Замер прямыми запросами по живой базе: `'%мнем%'` → 0 записей при живой «Мнемоническое правило…»; то же для `'%всегда%'`, `'%мой%'`. Пять пользовательских фраз из шести начинаются со значимого слова.

Наблюдённый промах целиком: «Какое мнемоническое правило ты знаешь?» — терялось слово «мнемоническое», оставалось одно «правило» из трёх, доля вопроса 33%, отсев по узости, **в память не уходило ничего**. С починкой доля 67%, запись приходит.

Починка: на каждой ступени лестницы спрашиваются два варианта префикса — как есть и с заглавной первой буквой. `UPPER()`/`LOWER()` в SQLite такие же ASCII-only, поэтому второй вариант готовится в Kotlin. Не закрыты: ВЕСЬ КАПС и заглавные внутри слова.

### 2.2 Ответ без опоры теперь называется в ленте — ЗАКРЫТО

Ответ, под которым не было ни одной записи памяти, ложился в ленту как обычная реплика ассистента — в позиции наибольшего доверия, где его не видит ни память, ни `RiskTrigger` (те стоят на пути записи в базу, а лента в базу не идёт). Провенанс доводился до модели для чужих утверждений и отсутствовал для её собственных.

Решение: предложение «Прошлый ответ ты дал без записей из памяти.» в начале **следующей реплики пользователя**. Подражать нечему — в собственных репликах модели пометка не появляется ни разу. Та же причина, по которой провенанс записи оформлен фразой «Пользователь сказал», а не меткой: работу делает грамматика.

Условие — пустой `Turn.records` прошлого хода, а не отсутствие новых: запись, легшая на первом ходе, на шестом не подставляется повторно, но модели видна и опорой быть не перестаёт.

Пометка ничего не останавливает и выдумывать не мешает. Она удерживает ленту правдивой, чтобы неподтверждённый ответ не превращался в установленный факт из собственных прежних слов модели.

### 2.3 Прибор для этой пометки — ЗАКРЫТО

Строка «Запрос:» в панели «Подробно» получила хвост `· пометка: прошлый ответ без опоры`. Проверяется по `userContent.startsWith(...)`, то есть по тексту, уходящему в движок: повторять здесь условие журнала бессмысленно — строка соглашалась бы с журналом и тогда, когда журнал ошибся.

### 2.4 Лента опаздывала на ход — ЗАКРЫТО

Во время генерации ход рисовался как начатый (`turn = null`), то есть без строки записей, а после `appendTurn` ленту никто не перерисовывал. Человек читал свежий ответ, не видя `[записей нет]` под ним, — признак приходил на следующем ходе. Тем же дефектом у только что закрытого хода не работало кликабельное «показать».

Починка: `binding.textResults.text = renderJournal()` после закрытия хода. Приём уже применялся в соседней ветке (когда модель не выдала ни знака).

### 2.5 `\b` с кириллицей в `RiskTrigger` — ЗАКРЫТО

`extractNumbers` искал числительные словами через `Regex("\\b${word}\\b")`. В Java `\b` определена через `\w`, а `\w` без флага `UNICODE_CHARACTER_CLASS` — это `[a-zA-Z_0-9]`. Между пробелом и русской буквой границы слова не возникает. Проверено на JVM 21:

```
\bпять\b в "в радуге пять цветов" -> не найдено
\bпять\b в "пять"                 -> не найдено
\bfive\b в "there are five colors" -> НАЙДЕНО
```

Карта `WORD_NUMBERS` из тридцати с лишним строк не срабатывала ни разу; проверка несовпадения чисел работала только на цифрах.

Починка вышла проще предложенных: регулярка **убрана**, а не починена флагом. `tokenize` уже режет по `\p{L}\p{N}` — юникодным по определению, — достаточно проверить членство в готовом множестве слов.

## 3. Измерения

**База (выгрузка 29.08 15:54, 13 записей).** Семь логов TOTE, шесть пользовательских фраз. Все под тегом `general`. Записей с цифрами — 7 (все логи), с числительными словами — **0**. Спорных (`reviewPending = 1`) — 0. **В RED нет ни одной записи**, то есть постоянный канал принципов всегда возвращает пусто и `PRINCIPLE_LIMIT = 3` пока ни на что не влияет.

**`STOP_DESCENT` — неподтверждаем на этой базе.** Прогон значений 1, 2, 3, 4, 5 на восьми вопросах: итоговый набор записей **не меняется нигде**. Меняется только объём поднятой работы (1 кандидат против 5). Причина: на 13 записях значимое слово находит ноль или одну запись, порог в три срабатывает только на мусоре (четырёхбуквенный обрубок «пере» внутри «переменной» в логах). `CANDIDATE_LIMIT = 20` тоже ни разу не упирается.

**Число не настраивать.** Условие, при котором оно начнёт что-то значить: когда ступень станет регулярно находить две-три записи, то есть когда пятибуквенный префикс попадает в несколько разных записей.

**Порог `CONTRADICTION_JACCARD_THRESHOLD` подтверждён.** Замер на восьми заведомых противоречиях, шести заведомо безобидных парах и всех 78 парах живой базы, с воспроизведением стеммера из `RiskTrigger`:

| Порог | Поймано из 8 | Ложных из 6 | Ложных на базе из 78 |
|---|---|---|---|
| 0.3 | 8 | 1 | 5 |
| 0.4 | 6 | 0 | 4 |
| **0.5** | **6** | **0** | **0** |
| 0.6 | 5 | 0 | 0 |

0.5 — наибольшее значение с нулём ложных и на выдуманных парах, и на живых. Ниже 0.5 ложные начинаются на живом материале: логи прогонов «успех за 3 итераций» и «успех за 5 итераций» становятся противоречащими. **Порог не трогать.**

Починка `\b` даёт при том же пороге 6 пойманных вместо 4 — половину прироста без единой настройки.

**Стеммер на числительных не нужен.** На замере не добавил ничего. Помогает только в косвенных падежах, и там же молча ломается: «трёх» и «три» расходятся по букве ё. Механизм, закрывающий часть случаев и не закрывающий остальные без признака, хуже отсутствующего.

**Проверка состава запроса.** Три хода подряд, лента чистая: без записей — хвоста нет; после безопорного хода с записями — `новых записей 1 из 1 на 129 зн. · вопрос 38 зн. · пометка: прошлый ответ без опоры`; после опорного — хвоста снова нет. 129 знаков сошлись знак в знак: 43 (пометка) + 2 + 82 (запись) + 2.

## 4. Решения

**4.1 Конвейер проверок.** Каждая ступень ловит своё максимально дёшево; до дорогой доходит только то, что дешёвыми средствами не решается.

| Ступень | Вопрос | Чем считает | Состояние |
|---|---|---|---|
| 1. Отбор | относится ли запись к вопросу | арифметика | **готова** |
| 2. Форма опоры | может ли ответ вообще быть в этом тексте | правила по форме | не начата |
| 3. Форма ответа | не выдумано ли явно (числа, перечни, имена вне опоры) | сличение по форме | не начата |
| 4. Судья | следует ли ответ из опоры | вторая модель | не начата |

**4.2 Дешёвая ступень имеет право только останавливать, но не одобрять.**

**4.3 Ступень 1 при сомнении приносит, а не теряет.** Ошибка в сторону пропуска невосстановима.

**4.4 Инструкция в промпте — не ступень конвейера.**

**4.5 У судьи три исхода, а пометку ставит код.** Подтверждённый памятью идёт как есть; неподтверждённый — с пометкой; противоречащий памяти останавливается. Источник определяет код, пометка приписывается снаружи.

**4.6 Формулировки в `BIBLE.md` — утвердительные.**

**4.7 Логи прогонов не удалять.** Экспорт наружу выполнен 29.08.

**4.8 (новое) Конвейеры записи и ответа — разные, и порча в памяти вниз по трубе не ловится.** `RiskTrigger` стоит на пути записи и сверяет новую запись с лежащими. Ступени 1-4 стоят на пути ответа и сверяют ответ с опорой. Пропущенное противоречие ложится в память как равноправная запись, приходит в опору, и ответ на неё идёт как подтверждённый памятью. Судья сверит ответ с опорой, они совпадут, и он пропустит.

> **Проверяющий не может поймать порчу в том, чем он проверяет.**

Второй шанс у пути записи один — пункт 6 (сводный проход, сверка всех со всеми). Он не построен.

**4.9 (новое) Случая «опора противоречит сама себе» в 4.5 нет.** Если две противоречащие записи попадут в опору одного вопроса, сегодня этого не заметит никто: три исхода описывают отношение ответа к опоре, а не опоры к себе.

**4.10 (новое) Пометку об отсутствии опоры несёт грамматика, а не метка.** Утверждение о положении дел, в реплике пользователя. Указание («не полагайся на прошлый ответ») было бы мягким сигналом, взвешиваемым против цели ответить, — по 4.4 такому в проверках места нет. В тесте эта граница закреплена отдельной проверкой.

## 5. Ступень 2: материал и прогон по чек-листу

**Класс А — берётся кодом.** «Спросили число, в опоре числа нет».

**Класс Б — кодом НЕ берётся.** «Из какого дерева колодка?» — опора говорит «деревянной», породы нет, ответ выдуман. Отличить «рубанок как ответ» от «рубанок как не-ответ» — работа судьи.

**Новый материал за сессию.** «Какое мнемоническое правило ты знаешь?» при опоре «Пользователь сказал: „Мнемоническое правило помогает запомнить все цвета радуги"» дал два ответа подряд: «Мнемоническое правило… обычно называется „Красный, жёлтый, оранжевый…"» и «**Ваше** мнемоническое правило: „В пяти цветах радуги зелёный — красный — синий, жёлтый — оранжевый — белый"». Запись говорит только, что правило существует; текст правила выдуман и во втором случае **приписан пользователю**. Пометка «без опоры» тут не встанет никогда: записей было 1, ход опорный.

**Признак сдвинут с вопроса на ответ.** «Спросили число» ловит только первый случай; «в ответе число, в опоре его нет» ловит оба. Привязка к ответу лучше ложится на 4.5: пометку ставит проверяющий, вычисляя из исхода сверки.

**Прогон по `CHECKLIST.md` переставил план:**

- **форма другая** — заводится не проверка, а **шов** (названное место с определённым входом и выходом), проверка чисел кладётся в него первым жителем. Общего решения у класса нет, но шов архитектурен, а `if` в чужой функции нет;
- **порога не заводим** — здесь объявляется граница, а не угадывается поведение;
- **`extractNumbers` придётся открыть наружу** (сейчас `private`);
- **шум от лишних цифр станет главной бедой.** В `RiskTrigger` его гасил порог схожести впереди; в ступени 2 порога впереди нет, и каждая цифра из кода, даты, номера версии пойдёт в сравнение;
- **прибор должен различать три состояния**, а не два: чисел в ответе нет / числа сошлись / числа разошлись. Панель сейчас различает только «пометка есть / нет»;
- **две пометки не сводить в одну.** «Опоры не было» — про отсутствие того, чем проверяют. «Число не из памяти» — про то, что проверили и не сошлось;
- **перед постройкой — замерить частоту.** Если пометка встанет почти на каждый ответ, она обесценится. Арифметика и общеизвестное («сколько будет два плюс два» → «4») будут помечаться как неподтверждённые — формально верно, но при высокой доле это тот же изъян, что у механизма, который горит всегда.

**Упор:** замерить не на чем. **Ответы агента нигде не хранятся** — лента живёт в памяти процесса, в базе ответов нет ни одного. Значит следующий шаг не ступень 2, а способ накопить ответы для замера — и он же, вероятно, закрывает давнюю нужду в эпизодическом журнале.

## 6. Прогон пункта 7c (мотивация агента) по `CHECKLIST.md`

Первый прогон чек-листа по крупной задаче после его появления в корне
репозитория. Сделан **до** проектирования, кода не написано ни строки.

### Ответы по пунктам

**1. Безопасность и цена.** Плата — аудит: у самозапущенного цикла нет
внешнего повода, которым его потом объясняют. По `ARCHITECTURE.md` §0 при
ничьей полезность проигрывает целостности аудита.

Следствие, которого в наброске 7c не было: `TaskAuthorization` держит
область `type + requestedBy + taskSessionId`, а у самозапуска нет
подтверждающего человека. Значит мотивация запускает **только задачи, чьи
действия проходят `ActionGate` без авторизации**. `TermuxKotlinRunner` ей
недоступен по построению, а не по настройке.

Вторая плата — тепло. Watchdog не откалиброван, поэтому самозапуск
разрешён только в самой безопасной зоне.

**2. Класс или единичный случай.** «Агент сам начинает» — класс, решать
архитектурно. Но **типы поводов — не класс, а перечень**: противоречие в
памяти, залежавшийся слой, спорная запись — каждый свой. Форма поэтому та
же, что у ступени 2: **шов с одним первым жителем**, а не общий «двигатель
хотения».

**3. Искать готовое — и работает ли оно там.** Самый урожайный пункт,
урожай неприятный:

| Готовое | Состояние на живых данных |
|---|---|
| `reviewPending` + `getPendingReview()` — готовый накопитель поводов с готовым UI | **0 записей**, не срабатывал ни разу |
| пометка «прошлый ответ без опоры» | работает, но живёт в памяти процесса и умирает с ходом |
| `accessCount` / `lastAccessedAt` / затухание Prism | живая арифметика «что залежалось», годится как есть |
| `EnergyBudget.applySuccess()` | вызывается ниоткуда — **осознанно, решение от 24.08**: полезный успешный шаг выходит из цикла сразу, награждать внутри некого |
| слой снов | спроектирован; мотивация может оказаться его потребителем, а не соседом |

Ответ на вопрос пункта: решено наполовину, и работающая половина ничего
не накапливает. `applySuccess` при этом не находка — он числится мёртвым
намеренно с 24.08; для мотивации важно лишь то, что накопитель на него не
повесить.

**4. Эмерджентность или граница.** Оба, по разные стороны.

- **Русло эмерджентно**: тяга растёт снизу из дешёвых проверяемых
  признаков — залежалось, противоречит, ответ был без опоры.
- **Берега объявлены руками**: потолок накопления, минимальная зона
  watchdog'а, запрет на авторизуемые действия, максимум запусков в сутки.

Это объявление границы, а не угадывание поведения. **Порог мотивации
подбирать не надо** — шаг снимается.

**5. Куда ошибётся.** Настройка обратная в двух каналах:

- накопление ошибается в сторону **лишнего** — незаписанный повод потерян
  навсегда;
- запуск ошибается в сторону **пропуска** — несработавший запуск
  восстановим, сигнал никуда не делся.

Второе верно **только если сигнал переживает перезагрузку**. Отсюда шаг,
которого не было: **накопитель обязан лежать в базе**, лента процесса на
эту роль не годится.

Отмечено при прогоне: формулировка пункта 5 в `CHECKLIST.md` несёт
готовую настройку («дешёвая ступень отбрасывает лишь то, в чём уверена»).
Здесь она перевернулась. Сторона промаха — ответ задачи, а не пункта.

**6. Чем это будет видно.** Прибор различает **три** состояния, не два:
копить нечего / копится, вот сколько и от чего / упёрлось в потолок.
Повод называется словами («запись 11 не перечитывалась 12 дней»), иначе
пункт не выполнен.

Цифр здесь не называть: частоту поводов замерить не на чем, ответы агента
нигде не хранятся (долг 2).

**Прибор и накопитель — одна вещь, и она первая.**

**7. Что не слить.** Пять пар:

- накопление сигнала ≠ решение запустить;
- мотивация ≠ энергия — «не хочу» против «не могу»;
- повод ≠ задача, и несколько поводов не сводятся в один балл (та же
  строка, что про ранг слоя, вес риска и голос проверки);
- мотивация ≠ обслуживание памяти — обслуживание неоднородно, часть его
  механический проход без всякого цикла;
- болтовня ≠ задача (уже решено, остаётся в силе).

**8. Чего не умеет — рядом.** В KDoc шва:

- не отличает «нечего хотеть» от «накопитель сломан» иначе как через
  прибор;
- не видит поводов, которых нет в базе;
- **не умеет отбросить повод, который уже пытались закрыть и не смогли** —
  это `RepeatDetector` на другом уровне, и его нет;
- не запускает задачи, требующие авторизации.

Тесты на молчание: пустая база — молчит; повод ниже потолка — молчит;
после потолка — **один** запуск, не два.

## 8. Долги

1. **`KotlinCodingTask.kt` не проверена на устройстве.** Покажет себя при первом настоящем прогоне цикла (долгое нажатие «Цикл», 15-20 мин нагрева). Смотреть: новая запись должна быть одной строкой про задачу и итерации, без кода и без `stderr`.
2. **Ответы агента нигде не хранятся.** Блокирует замер частоты для ступени 2. Кандидат на эпизодический журнал.
3. **Пересказ другими словами не ловится нигде.** «У паука восемь ног» / «Пауки имеют четыре ноги» — схожесть 0.33, до сравнения чисел не доходит. Опустить порог нельзя. Формальными средствами не берётся; второй шанс только у сводного прохода (пункт 6), который не построен.
4. **Перенос провенанса не ловится ничем.** «**Ваше** мнемоническое правило» — выдумка, приписанная пользователю. Формального признака нет, остаётся судье.
5. **Короткие строки прогонов дадут ложные противоречия.** «[TOTE] Успех за 3 итераций» против «за 5 итераций» — схожесть 0.67, числа расходятся, срабатывает. В базе молчит только потому, что к каждой строке пришит итоговый код, разбавляющий совпадение. Убрать код из строки — и каждый успешный прогон начнёт помечать предыдущие спорными. Корень глубже `RiskTrigger`: **события и утверждения лежат в одной таблице и меряются одной меркой.** У событий не бывает противоречий, у них бывают разные значения.
6. **`extractNumbers` тащит все цифры подряд**, включая адреса и длины из вывода компилятора. В `RiskTrigger` гасится порогом впереди; в ступени 2 гасить будет нечем.
7. **Снимок памяти врёт наполовину.** Кнопка «Показать» отдаёт базу, пропущенную через отбор по тексту в поле ввода, а заголовок при этом про всю базу. Обход: чистить поле перед нажатием. Развилка: (1) всегда чистый снимок — правка в одну строку, теряем предпросмотр; (2) два прибора с явной подписью. Склонялись ко второму, отложено как косметика.
8. **Ревизия отрицаний в `BIBLE.md`.** Кандидаты: `soft-signal-never-outweighs-goal-limit`, `no-authority-via-text-claim`, `goal-not-dishonestly-closable`. Править только слой формулировки; не всякое отрицание переписывать.
9. **Запись 11 написана через латинскую `ë`** (U+00EB) вместо `ё` (U+0451): «Четвëртое предложение». Поиск по «четвёртое» не найдёт её никогда, ни при какой починке регистра. Причина — клавиатура; класс тот же, что у регистра: сравниваются байты.
10. **В RED нет ни одной записи** — канал принципов всегда пуст, весь контекст держится на одном канале из двух.
11. **Память хранит вопросы как факты** (наследие от 24.08): стикер `Как меня зовут?` лежит как утверждение.
12. **Пункт Б (потолок длины записи) не начат** и, возможно, не нужен.
13. **Наблюдение за слоями** — снимок памяти раз в несколько дней с пустым полем ввода.
14. **Повод, который уже пытались закрыть и не смогли, отбросить нечем.** Из прогона 7c: без этого мотивация будет предлагать одно и то же. `RepeatDetector` решает ту же задачу внутри цикла, но между запусками аналога нет.
15. **Пометка «без опоры» не переживает перезагрузку** — лента живёт в памяти процесса. Пока она единственный носитель признака, накапливать по ней нельзя.
