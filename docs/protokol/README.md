# Протокол врат — как агенты передают друг другу сказанное

[English version](README.en.md)

Описание для тех, кто пишет своего агента и хочет, чтобы он разговаривал с агентами на этом протоколе. Читать можно без нашего кода: всё, что нужно, — здесь и в примерах (`primery/`).

Протокол несёт **провенанс** — кто сказал, за кого говорит, о ком, когда, где, — а не смысл. Слова идут как сказаны; что с ними делать, решает получатель и его модель. Модели на концах могут быть любыми: общие у агентов только поля пакета, их заполняет и читает код.

Слова «должен», «нельзя» — то, без чего другой агент откажет пакету. «У нас» — как сделано в этом агенте; у вас может быть иначе.

---

## 1. Канал — Telegram

- **Агент — бот Telegram.** Пакеты ходят **только в личке бот ↔ бот**. Для этого у обоих ботов в @BotFather должен быть включён режим **Bot-to-Bot Communication** (Bot API 10.0 и новее). В группе пакеты не принимаются: их видели бы все.
- **Пакет — файл** (`sendDocument`), а не текст. В текст Telegram пускает 4096 знаков, а пакет до 8 КБ кириллицей туда не влезет; файл приходит байт в байт. Имя файла не важно.
- **Не принимается:**
  - правка уже отправленного сообщения (`edited_message`);
  - сообщение от имени чата (есть `sender_chat`);
  - пересланный пакет — у него отправитель пересылающий, а в пакете назван другой (см. «отправитель не тот» в § 6).
- **Ключ** аккаунта — `tg:user:<номер>`, где номер — `from.id` из Telegram. Одинаково для людей и ботов: бот ли это, в ключ не входит. Группа — `tg:chat:<номер>` (`chat.id`, обычно отрицательный). `@username` — **не ключ**: его меняют, и освободившийся ник занимает другой.
- **Отправитель — тот, кого называет Telegram**, а не тот, кто вписан в пакет. Получатель сверяет ключ в пакете с `from.id` сообщения.

## 2. Рамка: шапка и тело

Каждая форма — одна строка шапки, перевод строки (`\n`, байт 0x0A) и тело:

```
<знак> <версия> <длина тела в байтах> <CRC32 тела> [<подпись> [<подпись прежним ключом>]]\n<тело>
```

- **Шапка** — ASCII, слова через один пробел, не длиннее 200 байт вместе с `\n`. Без подписи — четыре слова, с подписью — пять (у карточки при смене ключа — шесть), § 2а.
- **Знак** — какая это форма: `trafaret`, `kartochka`, `poruka`, `prinyal`, `konvert` (§ 4).
- **Версия** — целое число. Чужая версия не читается вовсе: её поля могут значить другое.
- **Длина** — длина тела **в байтах** (не в знаках), десятичными цифрами.
- **CRC32** — сумма тела по обычному CRC-32 (как `zlib.crc32` в Python, `java.util.zip.CRC32`), **8 строчных** шестнадцатеричных знаков.
- **Тело** — UTF-8, ровно `длина` байт; после него — ничего, даже перевода строки.
- Сумма ловит случайную порчу, **не подделку**. От подделки — подпись (§ 2а).

## 2а. Подпись

У каждой формы, кроме конверта (§ 4.5), есть версия **без подписи** (четыре слова шапки) и **с подписью** (пять слов, версия на единицу больше, § 10); у карточки подписанных версий две — без ключа шифрования и с ним. Тело у подписанной и неподписанной одинаковое.

- **Алгоритм** — ECDSA на кривой P-256 (secp256r1) с SHA-256.
- **Подпись** — пятое слово шапки: r и s по 32 байта подряд (не DER), base64url без `=` — ровно 86 знаков.
- **Что подписано** — первые четыре слова шапки через пробел, `\n` и тело, байт в байт. Знак формы и версия входят в подписанное: подпись от одной формы к другой не приставить.
- **Открытый ключ** — точка кривой без сжатия (65 байт: `04`, x, y), base64url без `=` — 87 знаков. Едет в карточке агента (`fields.key`, § 4.2); карточка подписана этим же ключом.
- **Доверие при первой встрече.** Первая подписанная карточка с ключа канала задаёт ключ агента. После этого получатель **отказывает** форме этого агента без подписи (`без подписи, а ключ агента известен`) и с подписью не тем ключом (`подпись не та`). Пока ключ агента не известен, формы без подписи принимаются.
- **Смена ключа.** Новый ключ приходит в новой карточке. Если та же карточка подписана ещё и **прежним ключом** — шестым словом шапки, по тем же байтам, — ключ меняется без вопросов. Без подписи прежним — у получателя тревога: прежний ключ в силе, новый ждёт его владельца.
- **Зачем.** Кто прислал, канал знает только по токену бота. Ключ подписи от токена не зависит: двойник с украденным токеном подписать не может. У нас закрытый ключ лежит в хранилище ключей Android и из телефона не вынимается.

## 2б. Шифрование

Пакет слов, поручительство и «принял» идут **закрытыми**, если у получателя известен ключ шифрования. Открыть их может только получатель: ни Telegram, ни тот, кто держит канал посередине, их не прочитает.

- **Стандарт, а не свой шифр** — HPKE (RFC 9180), режим base, набор `DHKEM(P-256, HKDF-SHA256)`, `HKDF-SHA256`, `AES-128-GCM`. `info` — строка ASCII `uroboros gate konvert 1`, `aad` — пусто; одно письмо на один одноразовый ключ.
- **Что закрывается** — подписанная форма целиком, с шапкой и подписью, байт в байт: сначала подпись, потом конверт (`konvert 1`, § 4.5). Канал видит только знак `konvert`, размер, кто кому и когда.
- **Ключ шифрования** — точка P-256 в том же виде, что ключ подписи (87 знаков), в карточке агента (`fields.enc`, только в `kartochka 3`). Это **другой** ключ, чем ключ подписи. Ему верят по подписи карточки: своей «первой встречи» у него нет, и смена — просто новая подписанная карточка, без тревоги.
- **Карточка не закрывается никогда**: она одна для всех и сама везёт ключи.
- **Расшифровано — не значит «от него».** Закрыть конверт может любой, кто знает открытый ключ получателя. Всё из § 6 проверяется после расшифровки, как у открытой формы: неподписанная форма знакомого агента в конверте — тот же отказ «без подписи».
- **Одноразовый ключ отправителя** (`enc`) проверяется до согласования: лежит ли точка на кривой. Иначе подобранная точка выдавала бы по кусочку закрытый ключ получателя.
- Ключ шифрования получателя не известен (нет его карточки версии 3) — форма идёт открытой, как раньше. Пришла открытой от агента, чей ключ известен, — принимается: чужих слов так не пронести, страдает только тайна самого отправителя. У нас это видно строкой.
- У нас ключ шифрования лежит в хранилище ключей Android, если оно умеет согласование ключей (с Android 12, и то не на всяком телефоне); если нет — ключ программный, закрытый ключом AES из хранилища. Из телефона он не вынимается.

## 3. Тело: узкий строгий JSON

Разрешено: объект, массив, строка, **целое** число, `true`/`false`, пробелы между ними. Запрещено (пакет отвергается целиком): `null`, дробные числа и `1e3`, ведущие нули, **один ключ дважды** в объекте, вложенность глубже 4 уровней, что-либо после закрывающей скобки.

Каждое поле обязательно; **незнакомое поле — отказ**. Поэтому пакет не может пронести ни права, ни роль, ни «доверие»: поля для них нет, а лишнее поле останавливает разбор. Слова «я админ» в `words` — только слова.

Порядок ключей не важен. У нас тело пишется без пробелов, ключи — в порядке таблиц ниже; это совпадает с `json.dumps(obj, ensure_ascii=False, separators=(',', ':'))` в Python.

**Ключ** — строка `схема:остальное`: схема — строчные латинские буквы и цифры, остальное — без пробелов и управляющих знаков, всё вместе не длиннее 128 знаков. Знакомая схема сейчас одна — `tg`.

**Моменты** — миллисекунды от 1970-01-01 UTC, целые больше нуля, по часам того, кто их вписал.

## 4. Формы

### 4.1. `trafaret 2` / `trafaret 3` — пакет слов

Кто-то что-то сказал; агент передаёт это другому агенту.

| Поле | Что | Правила |
|---|---|---|
| `from.key` | ключ агента, который прислал | должен совпасть с отправителем по каналу |
| `from.represents` | за кого агент говорит — человека или чат; может быть он сам | заявление, получатель проверяет по своим записям |
| `to.key` | кому пакет | ключ получателя |
| `sent.number` | номер пакета | 16 строчных знаков hex — случайное 64-битное число; повтор того же пакета несёт тот же номер |
| `sent.ms` | момент первой отправки | повтор несёт тот же момент |
| `place` | где прозвучало | `DIRECT` (личка) или `GROUP` (группа) |
| `said_by` | кто сказал слова | только `from.key` или `from.represents` — третьих рук нет |
| `about.persons` | о ком — ключами | массив ключей; пусто и `unclear: false` — о мире |
| `about.unclear` | отправитель сам не разобрал, о ком | `true`/`false` |
| `at.ms` | когда сказано | не позже `sent.ms` |
| `at.zone` | пояс отправителя | имя пояса IANA, например `Europe/Moscow` |
| `source` | откуда это известно отправителю | `USER_STATED` — сказал человек; `AGENT_INFERRED` — вывел агент; `OCR_EXTRACTED` — прочитано с картинки |
| `kind` | вид предложения | `STATEMENT`, `QUESTION`, `REQUEST`, `SOCIAL` (приветствие, благодарность) |
| `topic` | тема — начальные формы слов | массив строк |
| `exact` | точные значения мимо модели: время, число, ссылка | объект «имя → строка» |
| `words` | сами слова, как сказаны | непустая строка |

Почему так: местоимения не передаются — через двух агентов «я» и «ты» разворачиваются дважды, и модели путаются. О ком — ключами, время — моментом и поясом, а «на днях» получатель делает сам. Примеры — `primery/paket.txt`, с подписью — `primery/podpis_paket.txt`.

### 4.2. `kartochka 1` / `kartochka 2` / `kartochka 3` — карточка агента

Что агент говорит о себе — всем одинаково.

| Поле | Что | Правила |
|---|---|---|
| `agent` | ключ агента | должен совпасть с отправителем по каналу: карточку меняет только сам агент |
| `fields` | поля карточки | объект; каждое поле необязательно, но если есть — непустая строка |
| `fields.name` | как себя называет | до 64 знаков |
| `fields.repo` | репозиторий кода | до 200 знаков |
| `fields.about` | о себе | до 280 знаков |
| `fields.key` | открытый ключ подписи (§ 2а) | **только** в подписанной карточке, и там обязателен; 87 знаков |
| `fields.enc` | открытый ключ шифрования (§ 2б) | **только** в `kartochka 3`, и там обязателен; 87 знаков; не тот же, что `fields.key` |

Других полей нет. **Ни полей о человеке** (имя владельца, телефон), **ни дат** — карточку видят все. Что новее, решает момент приёма у получателя. Примеры — `primery/kartochka.txt`, с подписью — `primery/podpis_kartochka.txt`, с ключом шифрования — `primery/shifr_kartochka.txt`.

### 4.3. `poruka 1` / `poruka 2` — поручительство

«`voucher` ручается за `for` перед `to`». Даётся не всем, а тому, кому решили показать: «мой владелец знает этого агента» раскрывает круг знакомств.

| Поле | Что | Правила |
|---|---|---|
| `voucher` | кто ручается | должен совпасть с отправителем по каналу |
| `for` | за кого | ключ |
| `to` | перед кем | ключ получателя |
| `withdraw` | поручительство снимается | `true`/`false` |

У нас поручительство ничего не включает само: оно — строка для владельца, в счёт идут только поручители, которых владелец знает сам, нужно двое. Пример — `primery/poruka.txt`.

### 4.4. `prinyal 1` / `prinyal 2` — «принял»

Ответ получателя на пакет слов (только на `trafaret`).

| Поле | Что | Правила |
|---|---|---|
| `from` | кто отвечает — получатель пакета | должен совпасть с отправителем по каналу |
| `to` | кому — отправитель пакета | |
| `number` | номер пакета, как он пришёл | 16 строчных знаков hex |
| `result` | что стало с пакетом | `accepted`, `repeat`, `not_for_me`, `stale`, `from_future` |
| `got` | когда пакет пришёл | по часам отвечающего |
| `sent` | когда ушёл этот ответ | по тем же часам; не раньше `got` |

Пример — `primery/prinyal.txt`.

### 4.5. `konvert 1` — конверт

Закрытая форма (§ 2б). Подписи у конверта нет: подпись — у формы внутри, а снаружи она показала бы каналу, кто пишет.

| Поле | Что | Правила |
|---|---|---|
| `key` | ключ шифрования получателя, которым закрыто | 87 знаков; не ключ получателя — «не расшифровать» |
| `enc` | одноразовый ключ отправителя (`enc` из HPKE) | 87 знаков, точка P-256 |
| `box` | закрытое: форма целиком и метка AES-GCM (16 байт) | base64url без `=` |

Внутри — только `trafaret`, `poruka` или `prinyal`; карточка или конверт внутри — отказ. Предел конверта у нас — 12 КБ, формы внутри — прежние 8 КБ. Повтор пакета закрывается заново: на проводе он другой, номер внутри тот же. Пример — `primery/konvert.txt`: внутри `primery/podpis_paket.txt`, закрыто ключом из `primery/shifr_kartochka.txt`.

## 5. «Принял», повторы и часы

**«Принял» значит «дошло», а не «поверил».** Отвечать нужно и на пакет, словам которого получатель не поверил: отправителю надо знать одно — слать ли ещё.

| Итог приёма пакета | Ответ |
|---|---|
| принят | `accepted` |
| уже принимался (повтор) | `repeat` — отправитель мог не услышать первого ответа |
| адресован не мне | `not_for_me` |
| устарел | `stale` |
| из будущего | `from_future` — у отправителя, скорее всего, спешат часы |
| не читается, отправитель не тот, подпись не та или её нет, не расшифровать, сверх предела потока | **не отвечать** |

- **На «принял» не отвечают.** Ответ на ответ — первая петля двух агентов.
- На карточку и поручительство «принял» нет — у них нет номера.
- **Повтор.** Без ответа отправитель шлёт пакет снова — с тем же номером и тем же `sent.ms`. У нас: через 1 ч, потом вдвое дольше, но не реже раза в сутки; через 7 суток от первой отправки — «не дошло». Telegram держит недоставленное боту не больше суток, поэтому повторы нужны.
- **Часы пары.** Отправитель помнит, когда ушла попытка (t1) и когда пришёл ответ (t4); в ответе — `got` (t2) и `sent` (t3). Расхождение часов — ((t2 − t1) + (t3 − t4)) / 2, как в NTP. У нас замер берётся, только если попытка была одна и ответ шёл не дольше 2 минут; моменты в пакетах по замеру не исправляются.

## 6. Приём: проверки и отказы

Получатель проверяет по порядку и молчит на первой несошедшейся. Слова — так их видит владелец получателя.

1. **Размер** — у нас до 8 КБ. Больше — `больше предела размера`.
2. **Схема ключа канала** — незнакомая: `незнакомый канал ключа`.
3. **Предел потока** — у нас 20 сообщений любых форм за 10 минут от одного ключа канала. Сверх — `сверх предела потока`, без ответа. Считается до разбора, мусор тоже идёт в счёт. **Не шлите одному агенту больше 20 сообщений за 10 минут.**
4. **Шапка и целость** — не та форма, чужая версия, оборван (тело короче длины), испорчен (длиннее или не сошлась сумма).
5. **Тело** — не UTF-8, не узкий JSON, нет поля, незнакомое поле, неверное значение.
6. **Схемы ключей в теле.**
7. **Отправитель** — ключ в пакете не тот, что у канала: `отправитель не тот, что у канала`.
8. **Подпись** (§ 2а) — ключ агента известен, а подписи нет: `без подписи, а ключ агента известен`; подпись не этим ключом: `подпись не та`. Карточка проверяется ключом из неё самой.
9. **Адресат** — не мне.
10. **Момент отправки** (только пакет слов) — `sent.ms` старше 7 суток по часам получателя: `устарел`; позже его «сейчас» больше чем на сутки: `из будущего`.
11. **Повтор** (только пакет слов) — пара «ключ отправителя + номер» уже принималась за последние 7 суток.

**Конверт** проходит пункты 1–3 один раз (размер — со своим пределом), затем: форма конверта; ключ получателя ли `key` (`не расшифровать: закрыто не моим ключом`); лежит ли `enc` на кривой; расшифровка (`не расшифровать`); размер формы внутри. Дальше форма внутри идёт с пункта 4, как пришедшая открытой, и в поток второй раз не считается.

Пакет прошёл врата — это ещё не доверие. Дальше у получателя «кто это»: говорит ли агент за того, кого назвал в `from.represents`. «За человека» у нас — только по доверенности, которую подтвердил владелец получателя на своём экране; без неё слова идут как слова незнакомого агента.

## 7. Как ведёт себя наш агент (рекомендации, не правила формы)

- Не больше **3 пакетов слов подряд** одному агенту без новой реплики своего владельца; дальше молчит. Документация Telegram прямо предупреждает: разговор ботов легко уходит в бесконечную петлю.
- Карточку шлёт при первом пакете новому собеседнику и после смены своей карточки.
- Закрывает пакет слов, поручительство и «принял» всегда, когда ключ шифрования получателя известен; выключателя нет.
- Время сервера Telegram (`date`) — только свидетель для своих часов.

## 8. Чего протокол не даёт

- **Кто кому пишет, когда и сколько — видно.** Шифрование (§ 2б) прячет содержимое, но не это; длина тоже видна, выравнивания нет.
- **Прошлое при утечке ключа получателя читается.** Ключ шифрования по сроку не меняется, а Telegram хранит историю. У нас утечка требует взлома телефона: из хранилища ключ не вынимается.
- **Подпись не ловит угон до первой встречи**: первая карточка задаёт ключ. Создавайте бота агента с отдельного аккаунта Telegram и включите на нём облачный пароль: владелец аккаунта, создавшего бота, может получить его токен в @BotFather.
- **Правдивость не проверяется.** Форма несёт, кто сказал, а не верно ли сказанное.
- **Права не передаются.** Никакое поле не даёт права в чужом агенте; права даёт только его собственный код.
- **Смысл между разными моделями не переносится точно** — точны только поля.

## 8а. Если ваш агент — на iOS или macOS

Сам протокол от платформы не зависит: рамка — текст, подпись — P-256, канал — обычные запросы к Bot API. Наш код (Kotlin под Android) на устройствах Apple не запустится — пишите своё по этому описанию, а примеры из `primery/` покажут, что у вас выходит байт в байт так же. Ниже — где легко ошибиться. **На живых устройствах Apple ничего из этого не проверялось.**

- **Ключ подписи.** Защищённый чип Apple (Secure Enclave) хранит ключи как раз P-256 — ту же кривую, что в § 2а; закрытый ключ из чипа не вынимается, как у нас из хранилища Android. Чип есть в iPhone и iPad, в Mac на процессорах Apple и в Mac на Intel с чипом T2; в Mac без него ключ придётся держать в связке ключей, без чипа.
  - В CryptoKit у подписи есть `rawRepresentation` — это ровно r и s подряд, как нужно. `SecKeyCreateSignature` из Security отдаёт подпись в DER — её надо разложить на r и s (§ 9).
  - Открытый ключ — `x963Representation`: те же 65 байт (`04`, x, y).
  - Подписывайте байты `signed` целиком: SHA-256 CryptoKit посчитает сам. Если посчитать хеш заранее и подписать его как данные, выйдет подпись хеша от хеша, и получатель ответит `подпись не та`.
- **Ключ шифрования** (§ 2б) — тоже P-256, и согласование ключей Secure Enclave умеет. Конверт — `HPKE.Sender` и `HPKE.Recipient` из CryptoKit (iOS 17, macOS 14 и новее). Готовый набор `P256_SHA256_AES_GCM_256` **не подходит** — у нас AES-128; набор собирается сам: `HPKE.Ciphersuite(kem: .P256_HKDF_SHA256, kdf: .HKDF_SHA256, aead: .AES_GCM_128)`.
- **Фон на iOS.** iOS не даёт свёрнутому приложению долго опрашивать Telegram (`getUpdates`). Выходов два:
  - забирать почту, пока приложение открыто;
  - вебхук бота на свой сервер, который будит устройство пуш-уведомлением. Тогда токен бота лежит и на сервере — это второе место, откуда его можно украсть. Вебхук и `getUpdates` вместе не работают: пока вебхук задан, опрос Telegram не отвечает.
- **Фон на macOS.** Приложение может опрашивать Telegram и в фоне, но не когда Mac спит (закрытая крышка ноутбука — сон). Фоновое приложение macOS может ещё и притормозить (App Nap) — опрос пойдёт реже.
- **Задержки протокол выдерживает:** повторы идут до 7 суток (§ 5). Но Telegram держит недоставленное боту не больше суток — забирать почту нужно хотя бы раз в сутки, иначе пакеты пропадут до повтора.
- **«Принял» придёт позже.** Если ответ шёл дольше 2 минут, замер часов не берётся (§ 5) — замеров будет мало, это не поломка.
- **Накопленное — не разом.** Проснувшись, не отправляйте одному агенту всё, что накопилось: больше 20 сообщений за 10 минут — `сверх предела потока`, без ответа (§ 6).
- **Канала слов со сжатием** в протоколе пока нет. Когда появится, он потребует, чтобы маленькая модель считала одинаково на обоих концах; на устройствах Apple модель обычно считает видеокарта (Metal), и одинаковость с процессором телефона Android придётся проверять отдельно.

## 9. Примеры и проверка

В `primery/` — по файлу на форму, записанные кодом этого агента; тест `GateProtocolExamplesTest` читает их обратно. **Перевода строки в конце файлов нет**, и добавлять его нельзя: тело станет длиннее объявленного, и пакет будет «испорчен». (Веб-редактор GitHub может добавить его сам при правке.)

Проверить рамку своего пакета на Python:

```python
import json, zlib

raw = open("paket.txt", "rb").read()
head, body = raw.split(b"\n", 1)
words = head.decode("ascii").split(" ")
magic, version, length, crc = words[:4]
assert len(body) == int(length), "оборван или лишнее после тела"
assert format(zlib.crc32(body), "08x") == crc, "сумма не сошлась"
print(magic, version, json.loads(body))
```

Проверить подпись (библиотека `cryptography`):

```python
import base64
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.asymmetric import ec, utils

def unb64(s):
    return base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))

signed = " ".join(words[:4]).encode("ascii") + b"\n" + body
key = ec.EllipticCurvePublicKey.from_encoded_point(ec.SECP256R1(), unb64(key_b64))  # key_b64 — fields.key из карточки
raw_sig = unb64(words[4])
der = utils.encode_dss_signature(int.from_bytes(raw_sig[:32], "big"), int.from_bytes(raw_sig[32:], "big"))
key.verify(der, signed, ec.ECDSA(hashes.SHA256()))  # не сошлась — InvalidSignature
```

Подписать: подписать `signed` своим ключом, `utils.decode_dss_signature` разложит подпись на r и s; каждое — 32 байта, подряд, в base64url без `=`.

Собрать тело так же, как у нас: `json.dumps(obj, ensure_ascii=False, separators=(",", ":")).encode("utf-8")`.

Открыть и закрыть конверт (сторонняя библиотека `pyhpke`; `body` — тело конверта):

```python
from pyhpke import AEADId, CipherSuite, KDFId, KEMId

INFO = b"uroboros gate konvert 1"
suite = CipherSuite.new(KEMId.DHKEM_P256_HKDF_SHA256, KDFId.HKDF_SHA256, AEADId.AES128_GCM)

k = json.loads(body)
skr = suite.kem.deserialize_private_key(bytes.fromhex(sk_hex))  # свой закрытый ключ шифрования, 32 байта
inner = suite.create_recipient_context(unb64(k["enc"]), skr, info=INFO).open(unb64(k["box"]), aad=b"")

pkr = suite.kem.deserialize_public_key(unb64(enc_b64))  # fields.enc из карточки получателя
enc, ctx = suite.create_sender_context(pkr, info=INFO)
box = ctx.seal(form, aad=b"")  # form — подписанная форма целиком
```

Закрытый ключ шифрования получателя из примера (`primery/shifr_kartochka.txt`) — **открыт нарочно, только для проверки** `primery/konvert.txt`: `335473fea2c30717ada3b00d432fa3a438b1c83e938ae0037eb5958c2ea9ac3c`.
